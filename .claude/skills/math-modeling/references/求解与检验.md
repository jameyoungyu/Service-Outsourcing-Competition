## 一、工程约定

比赛环境下的目录结构，够用且不啰嗦：

```
项目/
├── data/              题目附件原始数据（只读，绝不修改）
├── code/
│   ├── explore_data.py    阶段 1 的数据探查
│   ├── solve_p1.py        问题一
│   ├── solve_p2.py        问题二
│   └── common.py          共用的数据加载、评价函数
├── figures/           所有图（PNG，300 dpi）
├── results/
│   └── results.json   所有要写进论文的数字
├── notes/
│   └── 题目拆解.md
└── 论文.md
```

**原始数据只读。** 清洗后的数据另存 `data/clean/`，清洗过程写在代码里而不是
手工改 Excel——手改的 Excel 无法复现，也无法写进附录。

**一个子问题一个脚本，能独立运行。** 评委可能只跑其中一个。
脚本顶部写清楚它读什么、写什么、对应论文哪一节。

**随机的东西一律固定种子。** 遗传算法、K-means、bootstrap、
train_test_split 全部显式传 `random_state` / `seed`。
没固定种子的结果，重跑一遍数字就变了，附录代码和论文对不上。

## 二、results.json 约定

所有要写进论文的数字先落到这个文件，论文从这里取数。这样做的收益：

- 论文里的数字有唯一来源，改了模型重跑一次，能立刻知道哪些数字要改；

## 三、按题型的检验清单

检验不是走过场——"结果的正确性"是明确的评阅要点，而且检验做扎实了，
灵敏度分析和模型评价这两节就有素材可写。

### 优化问题

1. **可行性回代**：把最优解代回**每一条**约束逐条检查，打印违反量。
   这条最重要，因为约束写漏了求解器不会报错，它会给你一个漂亮但无效的解；
2. **最优性证据**：MILP 报 gap（gap = 0 即全局最优）；启发式报收敛曲线；
3. **基线对比**：至少和一个简单策略比（贪心、随机、题目给的现有方案）。
   没有对比，"最优"这个词没有分量；
4. **小规模精确解对照**：如果主算法是启发式，构造一个能穷举的小实例，
   验证启发式在小实例上能找到已知最优解；
5. **边界情形**：预算取 0、容量取无穷时，解应该退化成可以口算的结果。

```python
def verify_feasibility(solution, constraints):
    """把解代回约束，返回违反清单。写进论文附录。"""
    violations = []
    for name, fn, rhs, sense in constraints:
        lhs = fn(solution)
        ok = (lhs <= rhs + 1e-6) if sense == "<=" else (lhs >= rhs - 1e-6)
        if not ok:
            violations.append({"constraint": name, "lhs": lhs, "rhs": rhs, "sense": sense})
    return violations
```

### 预测问题

1. **独立验证集**。时间序列按时间切分，绝不随机切分；
2. **多个误差指标**：RMSE（同量纲）、MAE（抗异常值）、MAPE（相对，跨量级可比）、R²；
3. **与朴素基线比**：时间序列比"用上一期值预测下一期"（naive forecast），
   截面数据比"用均值预测"。**打不过朴素基线的模型不能用**，
   而这个对比每年都有队伍不做；
4. **残差诊断**：残差应该没有明显模式。画残差图和 ACF 图，
   残差还有自相关说明模型没把信息榨干；
5. **区间覆盖率**：如果给了 95% 区间，在验证集上实际覆盖率应该接近 95%。

### 评价问题

1. **排序稳定性**：权重随机扰动 ±20%，跑 1000 次，统计前三名的稳定率；
2. **指标贡献分解**：每个对象的总分拆成各指标贡献，看是不是某个指标在主导；
3. **方法交叉验证**：换一种赋权法重算，用 Spearman 秩相关比较两组排序；
4. **常识对照**：结果里有没有明显违反常识的排名？有的话去查是数据问题还是模型问题，
   这个排查过程本身值得写进论文。

### 机理模型

1. **量纲一致性**：逐个方程检查；
2. **守恒量检验**：质量/能量/概率守恒的，数值解里守恒量的漂移应该很小；
3. **极限退化**：参数取极端值时退化成已知简单情形；
4. **网格/步长收敛**：步长减半结果基本不变。报一张步长 vs 结果的表；
5. **与解析解对照**：如果存在简化情形的解析解，数值解应该逼近它。

## 四、灵敏度分析怎么做

目标是回答"结论有多可靠"，不是"画几条曲线"。

**选对象**：挑你最不确定的 2–4 个参数。判断标准是"这个数是怎么来的"——
自己估的、文献取的、题目没给死的，优先级最高；题目明确给定的常数不用扫。

**三种做法，按投入产出排**：

1. **单因素扫描**（必做）：一次动一个参数，在合理范围内取 5–10 个点，
   看目标值和最优决策怎么变。产出是"参数在 X 范围内结论不变，
   超过 Y 后切换为 Z 方案"；
2. **双因素热力图**（选做）：两个参数联合扫描，画热力图，
   能看出参数间的交互。视觉冲击强，适合放正文；
3. **全局灵敏度**（加分项）：Sobol 指数或 Morris 筛选（`SALib` 库），
   给出各参数对输出方差的贡献占比。比单因素扫描更严谨，
   因为它考虑参数同时变化的情形。

**产出必须是可检验的句子**，例如：

> 运输成本系数在 ±30% 范围内变化时，最优路径选择保持为方案 A；
> 当该系数增至基准值的 145% 时，方案切换为 B，此时总成本增加 8.7%。
> 由于该系数取自 2024 年行业统计年报，实际波动幅度通常在 ±15% 以内，
> 因此本文结论在现实参数范围内是稳定的。

注意最后一句：把参数的**现实波动范围**和**结论的稳定范围**放在一起比较，
才算完成了论证。只说"在 ±30% 内稳定"而不说现实中会不会超过 30%，
论证是半截的。

**发现结论不稳时照实写。** 这是加分不是减分——见 SKILL.md 第二条纪律。

## 六、复现性

附录代码要能在评委的机器上跑出论文里的数字。三件事：

1. **固定所有随机种子**（见第一节）；
2. **路径用相对路径**，以项目根目录为基准。
   绝对路径既跑不通，又可能泄漏身份（`/Users/zhangsan/...`）；
3. **写一个 `code/run_all.py`**，按顺序跑完所有脚本、重建 `results/results.json`
   和所有图。提交前在干净目录下跑一遍，确认论文里的数字都能对上。

```python
# code/run_all.py
import subprocess, sys, pathlib
ROOT = pathlib.Path(__file__).resolve().parent.parent
for script in ["explore_data.py", "solve_p1.py", "solve_p2.py", "sensitivity.py"]:
    print(f"=== {script} ===")
    subprocess.run([sys.executable, f"code/{script}"], cwd=ROOT, check=True)
print("全部完成，结果见 results/results.json")
```
